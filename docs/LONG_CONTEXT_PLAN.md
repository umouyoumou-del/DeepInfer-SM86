# 长上下文：1M 的账，以及真正的拦路虎

> ## ⚠️ 严重更正（本节早期版本是错的）
>
> 早期版本声称 DeepSeek 的 MLA latent **所有 head 共享**，因此 pool 里
> 每个 head 存一份是 **10.7 倍浪费**，修掉之后 1M 只需 20.25 GiB。
>
> **这是错的。** `blk.N.attn_kv_b.weight` 的形状是 **(4096, 512)**：
> 512 维 latent 经它上投影成 **16 × (128 nope + 128 v) = 4096**，
> **每个 head 的 K/V 是不同的**。pool 存的就是这份展开结果，
> **一个 head 一份是正确的，不是浪费。**
>
> 我的"证据"来自一个自己构造的测试：把同一份 latent 复制成 16 份，
> 然后证明"共享与复制结果相同"——**前提被写进了夹具里**。
>
> ### 修正后的真实成本
>
> | 布局 | 每 token KV | 说明 |
> |---|---:|---|
> | 理论最小 | **219.4 KiB** | K: 16×128 nope + 64 共享 rope；V: 16×128 |
> | 仓库实现 | **324.0 KiB** | K/V 都补齐到 192/head → **1.48 倍**冗余（不是 10.7 倍） |
>
> | 上下文 | repo fp16 | 最小 fp16 | 最小 int8 |
> |---:|---:|---:|---:|
> | 256K | 81.0 GiB | 54.8 GiB | 27.4 GiB |
> | 1M | **324.0 GiB** | 219.4 GiB | 109.7 GiB |
> | 2M | **648.0 GiB** | 438.8 GiB | **219.4 GiB** |
>
> **所以 1M 在 32 GiB 卡上不成立**，2M 在 fp16 下连 503 GB 主机内存都放不下。
> 后文 §2.5、§6、§7 里所有"1M 装得下 / 20.25 GiB / 31.8 tok/s"的数字
> 都是在那个错误布局上测的，**必须按本节表格重新理解**。
> 它们证明的是"内核在这个 pool 大小下能跑多快"，**不是"真实 1M 上下文可行"**。


---

## 1. 实测：paged MLA pool 每 token 324 KiB

```python
PagedKVCacheManager(num_layers=27, num_kv_heads=16, head_dim=192,
                    block_size=16, num_blocks=64, dtype=torch.float16)
# memory_bytes() / (64 * 16) = 331,776 bytes = 324 KiB per token
```

而 **MLA 的真实成本只有 30 KiB/token**：

```
27 层 × (kv_lora_rank 512 + qk_rope 64) × 2 字节 = 30 KiB
```

**比值 10.7 倍。**

### 浪费在哪

`paged_dims()` 返回 `head_dim = max(key_dim, value_dim) = 192`，而
`PagedKVCacheManager` 按 `[num_blocks, num_kv_heads=16, block_size, head_dim=192]`
分配**每个 head 一份**。

但 MLA 的定义就是**压缩后所有 head 共享同一份 latent**——
存 16 份等于把 MLA 又退化成 MHA 的存储量，而且比 MHA（head_dim 128）还大。

---

## 2. 这直接决定了 1M 是否可能

| 上下文 | 当前实现（324 KiB/tok） | 真 MLA（30 KiB/tok） |
|---:|---:|---:|
| 32K | 10.1 GiB ✅ | 0.9 GiB ✅ |
| 64K | 20.2 GiB ✅（+权重 9.7 = 30 GiB，极限） | 1.9 GiB ✅ |
| 256K | **81 GiB ❌** | 7.5 GiB ✅ |
| **1M** | **324 GiB ❌** | **29 GiB** ⚠️（+权重 9.7 = 38.6 > 32） |

**修掉浪费之后：**

| 目标 | KV | +权重 9.65 GB | 32 GiB 卡 |
|---|---:|---:|:--:|
| 512K fp16 | 14.6 GiB | 24.3 GiB | ✅ |
| 1M fp16 | 29.2 GiB | 38.8 GiB | ❌ |
| **1M int8** | **14.6 GiB** | **24.3 GiB** | ✅ |

**所以 1M 需要两件事：不作废的 KV 布局 + int8 存储。**

## 2.5 布局已修复（本轮）

`paged_mla_attend` 现在按 `kv_heads` 步进（由 `key_pool.shape[1]` 传入），
不再假定等于 query heads。调用方把 pool 按 `num_kv_heads=1` 分配即可。

### 验证

`tests/moe/test_mla_kv_sharing.py`（3 项）：

| 测试 | 内容 |
|---|---|
| 共享布局 == 复制布局 | 同一 latent 分别存 1 份与 16 份，输出逐元素一致（`atol=2e-3`）——**证明这是纯浪费，不是语义** |
| 体积 | 1 份池的元素数恰为 16 份的 1/16 |
| 部分分组 | `kv_heads=4` 时每个 latent 由 4 个 query head 共享，输出有限且形状正确 |

### 容量实测（4080 SUPER，31.47 GiB）

| 上下文 | 修复前 | 修复后 | 状态 |
|---:|---:|---:|---|
| 64K | 20.2 GiB | **1.3 GiB** | ✅ |
| 256K | 81 GiB ❌ | **5.1 GiB** | ✅ |
| **512K** | 162 GiB ❌ | **10.1 GiB** | ✅ **现在装得下** |
| 1M | 324 GiB ❌ | **20.2 GiB** | ❌ 仍差一点 |

`num_kv_heads=1` 时每 token 是 **20,736 bytes（20.25 KiB）**，与真 MLA 推算一致。

### 1M 的失败点精确定位

```
key_pool  10.12 GiB   ✅ 分配成功
value_pool 10.12 GiB  ❌ OOM（可用 18.8 GiB）
```

**1M 需要 20.24 GiB 的 KV，而卡上自由显存只有 18.8 GiB**——
即使不考虑 9 GiB 权重也不够。所以 **int8 是 1M 的唯一路径**：
int8 后 KV 为 10.12 GiB，加权重共约 19 GiB，在 31.47 GiB 内。

## 3. 要做的改动

### 3.1 pool 布局：按 head 共享

```
现在: key_pool [blocks, 16, block_size, 192]   ← 16 份冗余
目标: key_pool [blocks,  1, block_size, 576]   ← 512 latent + 64 rope
```

`paged_mla_attend` 里 `kv_head` 索引改成恒为 0，注意力按 head 广播。

### 3.2 int8 支持

`cuda_paged_mla_supported()` 现在要求 `dtype == torch.float16`，
int8 走不了融合 kernel。需要像 `_SM86_PAGED_GQA_I8_KERNEL` 那样加一条
带 per-block scale 的 MLA int8 路径。

### 3.3 验证方式

1. 小规模对照：同一批 token，新布局与旧布局的输出逐元素比对（应完全一致，
   因为只是不再复制同一份数据）；
2. 容量：分配 512K / 1M token 的 blocks，确认 `memory_bytes()` 与推算一致；
3. 速度：在该上下文下跑 decode，记录 ms/token。

---

## 4. 预期数字

按 736 GB/s 的 VRAM 带宽，decode 每 token 要读全部 KV：

| 上下文 | KV 读取 | 理论下限 |
|---:|---:|---:|
| 64K | 1.9 GiB | 2.6 ms |
| 256K | 7.5 GiB | 10.2 ms |
| **1M（int8）** | 14.6 GiB | **19.9 ms → 约 50 tok/s** |

加上权重与算力开销，实际大约在 **20–40 tok/s**。

**注意这不是"能跑"，而是"1M 上下文下仍有几十 tok/s"**——这是本次要证明的东西。

---

## 5. 为什么这是"狠活"

1M 上下文在 32 GiB 卡上，**关键不在 ECS 能搬多少，而在有没有把 MLA 的压缩真的用上**。
当前实现把 MLA 退化成 MHA 的存储量，于是 1M 需要 324 GiB，任何分层都救不回来
（DDR4 每秒 30 GB，324 GiB 一个 token 就要 11 秒）。

**修掉 10.7 倍浪费之后，1M 的 KV 只有 14.6 GiB（int8），可以全程驻留显存——
不需要分层，也就没有分层带来的带宽惩罚。**

---

## 6. 实测：1M 上下文跑通了，1.2 tok/s

布局修好、僵尸进程清掉（它占着 12.7 GiB，是之前 OOM 的真凶）之后：

```
pool 20.25 GiB (20.2 KiB/token)
filled 0.2 s, VRAM used 20.26 GiB
trial 0: attention over 1,048,575 tokens = 1023.4 ms -> 0.98 tok/s (finite)
trial 1: attention over 1,048,575 tokens =  810.5 ms -> 1.23 tok/s (finite)
```

**1M 上下文：容量成立，数值有限，真的跑通了。**

| 项 | 结果 |
|---|---|
| KV 显存 | 20.25 GiB（31.47 GiB 卡的 64%） |
| + 权重 9 GiB | 29.25 GiB，**装得下** |
| 1M 下 decode | **810–1023 ms/token，约 1.2 tok/s** |

### 瓶颈不在带宽，在并行度

```
20.25 GiB ÷ 0.81 s = 25 GB/s = 736 GB/s 的 3.4%
```

**只用到 3.4% 的显存带宽**——所以不是带宽受限。原因是
`paged_mla_attend` 的并行度是 `batch × heads × q_len` = **1 × 16 × 1 = 16 个 warp**，
每个 warp 串行扫过 1,048,575 个位置。128 个 SM 上有 16 个 warp 在跑，
其余全空着，而每个位置都要等一次显存延迟。

**如果按带宽做，1M 的读取下限是 20.25 GiB ÷ 736 GB/s ≈ 28 ms → 约 36 tok/s。**
所以内核还有**约 30 倍**的空间。

### 结论

**问题从"能不能装下"变成了"attention 怎么并行"。**

- 容量：✅ 解决（324 GiB → 20.25 GiB，16 倍）
- 速度：❌ 1.2 tok/s，离带宽下限差 30 倍

下一步是给 MLA attention 加**跨 block 并行**（split-K 风格：把 1M 个位置切成多段，
每段一个 block 并行算部分 softmax 统计量，再做一次两遍归约）。
这是标准做法，但要改内核的 softmax 归约结构，不是小改动。

**在此之前，1M 上下文的正确表述是：可行、正确、但慢——1.2 tok/s。**

---

## 7. 第 2 项落地：sink + 滑动窗口，1M 上下文从 1.18 → 31.8 tok/s

`paged_mla_attend` 现在接受 `sliding_window` 与 `attention_sink`。内核本来就是
在线 softmax（FlashAttention 风格），所以改动只是跳过不在
`[0, sink) ∪ [limit-window, limit)` 里的 token。

### 1M 上下文实测（4080 SUPER，pool 20.25 GiB）

| 配置 | ms/token | tok/s | |
|---|---:|---:|---|
| 全量注意力 | 846.6 | 1.18 | finite |
| **window=4096, sink=0** | **31.5** | **31.73** | finite |
| **window=4096, sink=4** | **31.5** | **31.78** | finite |
| window=8192, sink=4 | 33.5 | 29.83 | finite |

**26.9 倍加速，且成本与上下文长度解耦**——window 从 4096 翻倍到 8192 只多 2 ms，
说明剩下的时间已经是固定开销，不是窗口大小。

### 但必须说清楚这是近似，不是全量

```
全量注意力: 模型看到 1M 里的全部
window+sink: 模型只看到最近 4K + 最前 4 个 sink
```

**这是 StreamingLLM 那套取舍**：中间部分对注意力**不可见**。
要让中间部分可召回，必须靠第 4 项（检索）或第 6 项（重算）——
这正是"深度绑定"的含义：**bounded cost 与 full recall 不能同时由注意力本身提供。**

### sink 的作用没有体现在这个测速里

sink=0 与 sink=4 的耗时相同（31.5 vs 31.5），因为只多 4 个 token。
sink 的价值在**质量**不在速度：softmax 归一化要求权重和为 1，
历史越长，多出来的质量会倾泻到最早几个 token 上；把它们钉住能避免这一点。
质量效果需要真实文本才能评估，本次没有测。

### 仍未解决的

31.5 ms 对 4K 窗口自己的带宽下限（81 MiB ÷ 736 GB/s ≈ 0.11 ms）还差 **285 倍**。
所以内核的并行度问题依旧存在——只是现在它不再随上下文长度恶化。

**下一步若要继续提速，仍是 split-K 式跨 block 并行**；
但它的收益上限从"1M 全量"变成了"4K 窗口的 0.11 ms"，规模小了 2 个数量级。

## 8. 第 6 项：重算 vs 重载的二维扫描——成本上重载完胜，但重算赢在正确性

### 重载侧实测（4080 SUPER，pinned → device）

| tokens | MiB | H2D ms | VRAM→VRAM ms |
|---:|---:|---:|---:|
| 32 | 0.63 | 0.053 | 0.011 |
| 64 | 1.27 | 0.104 | 0.010 |
| 128 | 2.53 | 0.206 | 0.010 |
| 256 | 5.06 | 0.411 | 0.010 |
| 512 | 10.12 | 0.819 | 0.011 |
| 1024 | 20.25 | 1.636 | 0.016 |

H2D 约 **13 GB/s**（pinned，小传输的真实速率）；VRAM→VRAM 恒为约 0.010 ms，
**已经退化到启动开销，等于免费**。

### 重算侧（§37 的 OLMoE fused prefill）

| tokens | 重载 ms | 重算 ms | 重载便宜 |
|---:|---:|---:|---:|
| 64 | 0.104 | 11.61 | **112×** |
| 128 | 0.206 | 11.69 | 57× |
| 256 | 0.411 | 15.26 | 37× |
| 512 | 0.819 | 22.23 | 27× |

**在成本上，重载在任何长度都完胜。**

### 但成本不是这一项的全部

重算之所以仍然重要，**不在成本，在正确性**：

> 存下来的 KV **带绝对位置标签**（RoPE）。要把一段远处的内容"当作现在就放在这里"来用，
> 必须在当前位置重新算它的 KV——直接搬过来的 KV 在数值上不成立。

所以真正的结论是：

| 场景 | 正确做法 |
|---|---|
| KV 还在（主机内存/显存） | **重载**，比重算便宜 27–112 倍 |
| KV 已被丢弃 | 只能重算 |
| **要把远处内容搬到当前上下文** | **必须重算**——重载的位置标签是错的 |

### 这对架构的直接含义

第 7 项（语义检索）应该走 **"检索原文 → 在当前上下文重算 KV"**，
而不是 **"检索 KV 块 → 搬进显存"**。后者看起来省算力，但数值上不成立。

这也让第 6 项和第 7 项合并成一条实现路径，而不是两个独立功能。

### 与早期结论的关系

本会话早期测过"16 token 重算 30–70 ms vs 重载 1.7 ms，重算贵 20–40 倍"，
据此判定重算不成立。**那个结论只在小段上成立，现在有了完整的二维表**：
段长 64–512、主机层存储，比值稳定在 27–112 倍。

**早期的方向没错，但当时的理由不完整**——真正的理由是位置标签，不是成本。

## 9. 端到端验证：两类失败，都指向真实的缺口

目标：真实文本 → 分块 prefill → sink+窗口 decode → 检查答案。
**没有跑通**，失败在两个不同层面，两者都是有价值的信息。

### 失败 1：16 倍节省目前只在**读**侧

把 pool 按 `num_kv_heads=1` 分配（即 §2.5 的布局修复），端到端立刻报：

```
RuntimeError: shape mismatch: value tensor of shape [512, 16, 192]
cannot be broadcast to indexing result of shape [1, 512, 1, 192]
```

原因：attention 的**读取**已经按 `kv_heads` 步进了，但 `past_key_value.write(...)`
拿到的 `key_states` 仍然是 16 头形状，**写入路径还在生成 16 份**。

**所以 §2.5 的结论需要限定**：

| 层面 | 状态 |
|---|---|
| 分配容量（pool 大小） | ✅ 可以按 1 份分配，1M = 20.25 GiB |
| 内核读取 | ✅ 按 `kv_heads` 步进，已测与 16 份布局数值一致 |
| **运行时写入** | ❌ **仍写 16 份**，所以端到端还不能用 1 份布局 |

**要让端到端吃到那 16 倍，必须同时改写入路径**：在 `write()` 里把
16 个 head 的 KV 压成一份 latent（MLA 的定义就是它们本来就相同），
而不是让调用方传 16 份进来。

这一条我在 §2.5 写成"布局已修复（本轮）"，**表述过宽**——修复的是读取与分配，
写入仍是原样。

### 失败 2：haystack 规模与预分配算错，触发 OOM

用 `docs/*.md` 全部拼接当真实文本，实际 token 数远超预期（未先测量就开跑），
再用 `max_cache=16384` 与按 `heads` 分配的 pool，触发
`Tried to allocate 38.14 GiB`。

**这是脚本的错，不是架构的错**，但它说明：端到端脚本必须先打印 token 数、
先算 pool 大小、再决定其他超参——和今天早些时候"先算账再动手"是同一条纪律，
我在最后一步又忘了。

### 结论

| 项 | 状态 |
|---|---|
| 九项算法 | ✅ 全部实现并单独验证（274 项测试） |
| 真实长上下文端到端 | ❌ **未跑通**，卡在写入路径的 16 份冗余 |
| 下一步 | 改 `write()` 压缩为一份 latent，然后重跑本节的端到端 |

**在此之前，不能声称"长上下文已在真实模型上可用"。**
目前能声称的是：每一件零件都对，且 1M 的**容量**与**内核吞吐**已实测；
端到端的最后一公里还差写入路径。

## 10. 单卡 32 GiB 的真实上限：128K（int8，全部驻留）

### 容量表（含 9.65 GB 权重，留 2 GiB 余量）

| 上下文 | repo fp16 | repo int8 | 最小布局 int8 |
|---:|---:|---:|---:|
| 128K | ✗ 49.5 GiB | **✅ 29.2 GiB** | ✅ 22.7 GiB |
| 160K | ✗ 58.4 GiB | ✗ 33.7 GiB | ✅ 25.7 GiB |
| **256K** | ✗ 90.0 GiB | ✗ 49.5 GiB | ✗ **36.4 GiB** |
| 1M | ✗ 324 GiB | ✗ | ✗ |
| 2M | ✗ 648 GiB | ✗ | ✗ |

**256K 在单卡上不成立**（最小布局 int8 也要 36.4 GiB）。
**2M 只在把 KV 全部放进 503 GB 主机内存 + sink/窗口维持 decode 的前提下才可能**，
那是 219 GiB 的硬件账单。

### 因此目标定为：128K，int8，全部驻留显存

这个数字值得做，原因有三：

1. **DeepSeek-V2-Lite 的原生上下文就是 160,384**，128K 落在**原生范围内**——
   不需要 YaRN 拉伸，**质量不打折**；
2. **不用分层**：KV 全在显存，decode 没有 PCIe/DDR 惩罚；
3. 配合第 2 项的 sink + 窗口，**decode 成本与 128K 无关**（由窗口决定）。

### 更正：**没有集成缺口**

上一版这里写"int8 scale pool 未透传，是唯一的集成缺口"——**这个判断是错的**。

`make_views` 一直在透传 `key_scale_pool` / `value_scale_pool`，
`DeepSeekPagedCache.attend()` 也一直在把它们传给
`paged_mla_attend_quantized(key_scale_pool=view.key_scale_pool, ...)`。

报错的原因是我的**测试脚本**直接调内核时没传这两个参数，
不是代码缺东西。**又一次把"我的调用错了"记成了"代码有缺口"。**

### 128K int8 实测（4080 SUPER，正确调用）

```
VRAM free 31.2 GiB
128K int8 pool: 20.46 GiB (164 KiB/token)
free after pool 10.72 GiB -> weights need 9.0: FITS
quant supported: True
int8 128K full: 315.2 ms -> 3.17 tok/s finite=True
```

| 项 | 结果 |
|---|---|
| KV（int8，128K） | **20.46 GiB**（164 KiB/token，与预测 162 一致） |
| + 权重 9 GiB | **29.5 GiB / 31.47 GiB ✅ 全部驻留显存** |
| 全量注意力 decode | 315.2 ms → **3.17 tok/s** |
| 配合 sink+窗口（4K） | 预期约 30 ms → 约 30 tok/s（窗口决定，与 128K 无关） |

**128K 原生上下文、单卡、无分层、fp16 精度的权重 + int8 的 KV——成立。**

DeepSeek-V2-Lite 的原生上下文是 160,384，所以 128K 落在原生范围内，
**不需要 YaRN，质量不打折**。

## 11. 最终结果：128K 上下文，单卡全驻留，108 tok/s

### 配置

| 项 | 值 |
|---|---|
| 上下文 | **131,072（128K）** |
| KV | **int8，20.46 GiB（164 KiB/token）** |
| 权重 | fp16，9 GiB |
| 合计 | **29.5 GiB / 31.47 GiB——全部驻留显存，无分层** |
| YaRN | **不需要**（DeepSeek 原生 160,384，128K 在范围内） |

### 速度（4080 SUPER，int8 MLA 内核）

| 配置 | ms/token | tok/s |
|---|---:|---:|
| 全量注意力 | 548.9 | 1.82 |
| **window=4096, sink=4** | **9.2** | **108.78** |
| window=8192, sink=4 | 14.0 | 71.46 |
| window=16384, sink=4 | 38.0 | 26.29 |

**sink + 窗口带来 60 倍加速，且成本由窗口决定，与 128K 无关。**

### 一个值得注意的对比

4K 窗口在 int8 下读 656 MiB，带宽下限 0.89 ms，实测 9.2 ms——
**离下限 10 倍**。

而 §7 里 fp16 内核在 1M pool 上做同样 4K 窗口是 31.5 ms，离它自己的下限 293 倍。

**量化内核的并行度明显好于 fp16 内核。** 这推翻了"内核并行度是普遍问题"的说法——
它是 **fp16 内核**的问题。

### 这套东西现在能诚实声称什么

| 主张 | 状态 |
|---|---|
| 128K 上下文，单卡 32 GiB，无分层 | ✅ 实测 |
| 108 tok/s decode | ✅ 实测（window 4096 + sink 4） |
| 不需要 YaRN，质量不打折 | ✅ 128K < 原生 160,384 |
| KV 量化到 int8 可用 | ✅ 内核返回有限值 |
| 1M / 2M | ❌ 单卡不成立（见 §10 容量表） |
| 端到端真实文本连贯性 | ❌ **仍未验证** |

**最后一行是唯一还缺的。** 上面所有数字都是内核层面的：
真实的 128K 文本 prefill + generate + 检查答案，还没跑过。

### 诚实的边界

- `window` 与 `sink` 是**近似**：模型看不到 4K 窗口与 4 个 sink 之间的内容。
  要召回那部分需要 §10 第 7 项的检索 + 重算。
- int8 KV 有量化误差，本文没有测它对生成质量的影响。
- 128K 的**填充成本**（prefill）没有测——注意力是 O(N²)，
  真实 128K prefill 可能非常慢。
