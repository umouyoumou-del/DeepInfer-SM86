# 百万级上下文、全量召回：latent MLA 缓存 + 全量注意力

> 接手 `docs/HANDOFF.md`（DeepSeek 交接）之后的工作。目标是用户提的：**1M / 2M 上下文，
> 全量召回**——每个 token 都留在注意力里，不是滑动窗口把中间丢掉。
> 硬件：RTX 4080 SUPER 32 GiB（31.47 可用，80 SM，sm_89，PCIe 4.0 x8 ≈ 13 GB/s），503 GB 内存。
> 模型：DeepSeek-Coder-V2-Lite-Instruct Q4_K_M（训练到 128K）。

---

## 0. 结论

**单张 32 GiB 卡，2M（2,097,152）token 上下文，9 根埋在不同深度的事实全部找到并逐字答对（9/9）；
1M 同样 9/9。** 训练长度只有 128K 的模型（Coder-V2-Lite），没有任何训练。

| | 1M | 2M |
|---|---|---|
| KV（latent fp8） | 17.3 GiB，全在显存 | 34.6 GiB，1.51M 在显存 + 0.58M 在主机内存 |
| 编码（prefill） | 8.9 min（有界）/ 35.1 min（全量） | 20.2 min（有界） |
| 召回（定位 + 重读） | **9/9** | **9/9** |
| 召回（问题直接全量注意力） | 1–2/9 | — |
| 缓存存盘 / 加载 | 30 s / 13.8 s | — |

做到这一步靠四件事，缺一不可：

1. **把 MLA 当 MLA 用**：缓存共享 latent，不缓存展开的逐头 K/V——每 token 324 → 17.3 KiB；
2. **DCA**：超出 128K 后相对位置不出训练范围（原样 RoPE 在 256K 就输出乱码）；
3. **有界编码**：编码时每个 token 只看前 96K + sink，库里每个条目都在训练分布内算出，
   prefill 也从平方变成线性；
4. **定位 + 重读**：问题用模型自己的注意力在**整个库**上定位（每个 token 都参与打分），
   再把定位到的原文放进短上下文作答。问题直接对 1M 个 key 做全量注意力，这个模型
   找得到大致位置、但逐字抄写会走样（§4.4）。

"全量召回"在这里的准确含义：**每个 token 都编码、都可被定位**；答案在短上下文里产生。
上表测的是单句事实的检索（§5）。

**更难的版本：同一份 2M 文档里同时放 39 根针**（RULER 式五类：16 个相似键、一键多值、一问多键、
5 环变量链带干扰链、两跳），一次 prefill 后问 21 题——**一次运行 21 题、31 个条目全部答对**。
为此改了定位打分、加了行级精读和按回答反馈的多轮定位；变量链那题各轮回答还在摇摆（§4.7）。
这 21 题的问答原来要 51 分钟，§4.8 降到 8.6 分钟（一题中位 18 s），结果同样 21/21；缓存存盘后同一份
文档再次使用只需加载 51 秒；编码窗口缩到 16K，新文档的 prefill 16.8 → 6.8 分钟。

**3M（3,145,728 token）**：同样 39 根针、21 题，两次运行（其中一次从头 prefill）都是 21/21、31/31，33 处针全部定位到（§4.9）。KV 51.9 GiB，锁页主机内存实占 42 GiB，
prefill 25 分钟。为此后续轮多做一次"只用最终答案"的定位、补 32 个块——3M 时变量链的下一环只能排进前 30。

## 2. 架构

代码：`deepinfer/moe/latent_mla.py`、`latent_mla_triton.py`、`latent_retrieval.py`、`latent_reread.py`、
`deepseek_longctx.py`；脚本：`scripts/needle_longctx.py`、`scripts/summarize_needles.py`；
结果：`docs/results/longctx/*.json`。

### 2.1 latent 缓存

每层每 token 存两样东西：`kv_a_layernorm` 之后的 512 维 latent `c`，和已旋转的 64 维 `k_pe`。

| 布局 | 每 token（27 层） | 1M | 2M |
|---|---:|---:|---:|
| 仓库原 paged 池（逐头展开，补齐到 192） | 324.0 KiB | 324 GiB | 648 GiB |
| latent fp16 | 30.4 KiB | 30.4 GiB | 60.8 GiB |
| **latent fp8 e4m3（每 128 维一个 fp32 scale）+ k_pe fp16** | **17.3 KiB** | **17.3 GiB** | **34.6 GiB** |

fp8 的切法与 FlashMLA 相同：k_pe 带位置，保留 fp16。超出 `gpu_tokens` 的部分放进 pinned 主机内存。

### 2.2 prefill：展开一块、FlashAttention、按 LSE 合并

prefill 是成千上万个 query 一起算，展开形式（每头 192/128）比吸收形式（576/512）省 3.4 倍算力。
所以每个 query 块对历史按 tile 处理：从缓存取一段 latent，用 `kv_b_proj` 展开成逐头 K/V，
跑 PyTorch 自带的 FlashAttention-2（`_scaled_dot_product_flash_attention`，返回 LSE），
各 tile 按 log-sum-exp 合并。V 补齐到 192 是 flash 后端的要求（白算 20%）。

本卡实测（`bench_sdpa.py`）：FlashAttention-2 **97–102 TFLOPS**，扣掉补齐后有效 **81–85 TFLOPS**；
展开的 GEMM 对 16K 的 query 块只占 ~2.5%。

### 2.3 decode：吸收形式 + Triton flash-decoding

单个 query 时把 W_UK 吸收进 query、W_UV 吸收进输出，16 个头直接在共享 latent 上做注意力：
每个缓存字节每 token 只读一次，供 16 个头共用。内核（`latent_mla_triton.py`）把 key 区间切给多个
program，每个 program 对 16 个头同时算（两个 dot 都走 tensor core，M = 16），fp8 在寄存器里反量化，
部分结果按 LSE 合并。与 fp32 参考实现相对误差 ~1e-3。

### 2.4 MoE prefill：张量核

运行时原有的融合 Q4_K 分组内核在 16K token 的块上只有约 **500 tok/s**（16K 块 31.9 s 里 MoE 占 31.2 s），
等于 2 TFLOPS。改成每块把该层用到的专家一次性反量化成 fp16、每个专家三次 cuBLAS GEMM：
16K token 每层 **69–81 ms vs 1,150 ms（14–17×）**，输出与原路径最大相对差 3.9e-4。

### 2.5 位置：dual chunk attention（DCA）

训练长度之外，旋转维的相对位置是模型没见过的。DCA（An et al., 2024）：key 按 `j mod chunk` 旋转，
query 根据 key 在**同块 / 前一块 / 更早**选三种旋转之一，使任何相对距离都 < 训练长度，
而**每个 token 仍在注意力里**。chunk = 训练长度的 3/4（Coder：128K、96K）。
**在训练长度以内它与原 RoPE 逐位相同**（单元测试逐对验证）。三种旋转对应三组 query，
flash/decode 按区段分别算再按 LSE 合并，算力不增加。

RoPE 角度在 fp64 下按需计算：官方模块每层各缓存一份 cos/sin（2M 时 27 层共 13.8 GiB），
且角度在 fp32 里形成，2M 处误差 ~0.06 rad。

### 2.6 KV 库：持久化、插入、检索

- **持久化**：`DeepSeekLongContext.save/load`。prefill 一次，存盘；之后加载即可提问，跳过 prefill。
  一块盘放不下时（2M fp8 34.6 GiB），`spill=[另一块盘]` 让每个数组按层分文件、依次写进放得下的盘（§4.8）。
- **插入**：`insert(ids, position)`——把一段文本当作出现在逻辑位置 `position` 来计算：它看得到前面
  真实的上文（缓存里逻辑位置更小的部分），之后所有 query 在那个位置看到它。物理槽位与逻辑位置
  分离（extents）。近似之处：插入点之后的旧 token 当初没看到它。
- **块检索**（`latent_retrieval.py`）：每 64 个槽位记一份逐维 min/max（Quest 上界），
  `ub = q⁺·max + q⁻·min` 两次小 GEMM 给所有块打分（1M 时 1.6 万块、<0.1 ms/层），
  query 精确地只看 sink + top-k 块 + 最近窗口。上界不会低估一个块——均值池化会把一句话的
  事实淹没在块平均里，所以不用均值做指纹。sink/窗口按**逻辑**位置判定（插入的内容在最新的
  槽位里、却在序列深处，不能白占窗口）。可选 `reposition`：把选中的块按原顺序挪到窗口前面，
  只需对 64 维 rope 换个 query 旋转。
- **定位 + 重读**（`latent_reread.py`）：问题逐层对**全部**缓存位置算精确的注意力质量
  （每层一遍：一个 Triton kernel 同时算问题的注意力和每块的质量，§4.8），按块累加（跨层、头、问题
  token），sink 不参与；取最重的块及邻块，
  按逻辑顺序拼回原文 token，新开一个短上下文作答。每个槽位记着自己的 token id（随缓存存盘）。

### 2.7 有界编码

`encode_window`：prefill / 插入时每个 token 只看前 64 个位置（sink）和它之前的 W 个 token；
提问不受限制。W = 96K 时最大相对距离约 114K，全部在训练范围内。超出训练长度后，
全量注意力 prefill 会让 128K 之后每个 token 的 KV 都在训练分布之外算出（§4.5 证实库条目因此变差），
有界编码同时把 prefill 从 O(N²) 变成 O(N·W)。

## 4. 实测

针（needle）都是**真实文本**里的一句事实：草堆是 CPython 标准库源码（按文件名排序，确定性），
每根针说一种不同的事（"Dr. Amber Lynx 把研究笔记放在 7624039 号柜"之类），答案是 7 位数字，
答对＝输出里出现完整的 7 位数。模型 Coder-V2-Lite（训练到 128K），DCA 的 chunk = 96K。
结果文件 `docs/results/longctx/*.json`，`scripts/summarize_needles.py` 汇总。

三种针的放法：

- **multi**：9 根针在同一文档里，一次 prefill，各问题分支提问；
- **single**：每根针一个文档（没有"答成别的针"的可能）；
- **insert**：草堆 prefill 一次，每根针用 `insert()` 插到它的位置后提问（它看得到真实的前文；
  近似之处是它之后的草堆当初没看到它）。128K 上 insert 与 single 结果一致（都全中）。

### 4.1 训练长度以内：系统 = 模型

| 长度 | 方式 | 召回 | 说明 |
|---:|---|---:|---|
| 8K | multi | 9/9 | 题目本身可答 |
| 32K | multi | 7/9 | 错的两题都答成了位置 4 那根针的码 |
| 128K | multi | 4/9 | 错的都答成**别的针**的码——模型混淆，不是丢失 |
| 128K | single | 5/5 | multi 里错的那 5 个深度，单独放全中 |
| 128K | insert，fp16 / fp8 | 9/9 / 9/9 | fp8 latent 无损 |
| 128K | insert，**块检索 top-64**（只看 ~8K / 128K） | **9/9** | 检索在训练长度内无损 |

32K 同模板 9 针，llama.cpp 与本实现逐题答案相同（都是同样 3 题答成同一个码），见 §3.2。

### 4.2 超出训练长度：位置编码

| 长度 | RoPE | 召回 | 输出 |
|---:|---|---:|---|
| 256K | 原样（YaRN 40×） | 0/3 | 乱码（`'can = name = _find = None = …'`） |
| 256K | **DCA** | **3/3** | |
| 512K | DCA，fp8 | 4/9 | 多数是"抄一半"：`6432178`（应为 6433012）、`2579468`（2579240） |

### 4.3 1M：容量、速度、持久化

| 项 | 值 |
|---|---|
| 上下文 | 1,048,576 token，全部 token 留在注意力里 |
| KV | fp8 latent + fp16 rope，17.3 GiB，**全部驻留显存**（专家权重改为从主机流式读取，空出显存） |
| 显存峰值 | 21.96 GiB |
| prefill（全量注意力） | **35.1 min**（498 tok/s；注意力 ~93%） |
| 缓存存盘 / 加载 | 30 s 写 18.6 GB / **13.8 s 读回**（对比 35 min 重新 prefill，150×） |
| decode（全量注意力） | 230–370 ms/token（注意力 + 流式专家） |

### 4.4 1M：召回——全量注意力不够，"定位 + 重读"够

同一份 1M 缓存（存盘后加载，不再 prefill），同样 9 根针：

| 提问方式 | 定位到 | 答对 | 现象 |
|---|---:|---:|---|
| 全量注意力 | — | 2/9 | 只有最后 ~100K 内的针答对；其余答非所问 |
| 全量 + log-n 缩放 / 改 DCA 远距上限 | — | 0–1/9 | 更差 |
| 块检索 top-64 | ~8/9 | 2/9 | 找对了针，但 7 位数抄到一半走样：`762403`、`7135246`、`2579643` |
| 块检索 + 重新定位（放到窗口前） | ~8/9 | 2/9 | 同上 |
| **定位 + 重读 top-8** | **9/9** | 8/9 | 唯一错的那题定位正确，模型开始"step by step"解释、被 32 token 截断 |
| **定位 + 重读 top-32** | **9/9** | **9/9** | 位置 4 到 1,038,097 全中 |

"定位 + 重读"（`latent_reread.py`）：问题用模型自己的注意力对**全部 1M 个缓存位置**逐层打分
（精确归一化的注意力质量，按 64 token 一块求和），取最重的块及其邻块，按原顺序把它们的
**原文**拼成 1.5–6K token 的短文档，在新的短上下文里作答。每题 11–17 s（插入 + 定位 + 重读）。

为什么全量注意力在 1M 不行而定位行：超出训练长度 8 倍后，模型仍能把注意力**指向**正确位置
（定位 9/9），但从 100 万个 key 里**逐字抄写**会走样（检索后也一样），而 8K 以内抄写是全对的。
另一个原因是全量注意力 prefill 时，128K 之后每个 token 的 KV 都是在超出训练分布的注意力下算出来的，
库里的条目本身就退化了——见 §4.5。

### 4.5 有界编码：库更好、prefill 线性

上面的解释可以直接检验：prefill 时让每个 token 只看 64 token 的 sink + 它之前 96K
（`encode_window`，最大相对距离 ~114K < 128K），所有 KV 都在训练分布内算出；
召回交给提问时的定位/检索。问题本身不受窗口限制。

| 1M，同样 9 根针 | 全量注意力 prefill（35.1 min） | **有界编码 96K（8.9 min）** |
|---|---:|---:|
| 问题用全量注意力 | 2/9 | 1/9 |
| 块检索 top-64 | 2/9（抄一半） | **4/9**（错的多是差一位：`6433019`、`2579241`） |
| 块检索 + 重新定位 | 2/9 | 4/9 |
| **定位 + 重读 top-8** | 8/9 | **9/9（定位 9/9）** |
| 定位 + 重读 top-32 | 9/9 | |

- 检索类提问在有界编码的库上明显更好——库里的条目确实是全量 prefill 弄坏的；
- prefill 从 O(N²) 变成 O(N·W)：1M **35.1 → 8.9 min**，2M 从 ~2.3 h 降到 ~16 min；
- **"全量召回"的含义因此变成：每个 token 都编码进库、都可被定位**，答案在短上下文里产生。
  问题用全量注意力直接从 1M 个 key 里读答案，这个模型做不到（两种库都只有 1–2/9）。

### 4.7 复杂大海寻针（RULER 式）：39 根针同时在场

§4.6 的 2M 9/9 是 **insert 模式**：每次只有一根针在库里。这一节把 39 根针放进**同一份**文档，
一次 prefill，再对同一个缓存问 21 个问题——每根针都是其它针的干扰项。脚本 `scripts/needle_complex.py`，
草堆仍是 Python 3.12 标准库源码，模型 Coder-V2-Lite-Instruct（训练 128K），DCA + fp8 latent +
有界编码 96K，与 §4.6 相同。

| 类型 | 内容 | 题数 | 条目 |
|---|---|---:|---:|
| MK 多键 | 16 条同模板事实 "The special magic number for <key> is: <7 位数>."，键共享单词（crimson falcon / crimson otter / silver otter …），逐个提问 | 16 | 16 |
| MV 多值 | 一个键 4 个值散在 4 处，旁边有近似键（golden walrus、azure viper）；问全部值 | 1 | 4 |
| MQ 多问 | 一个问题同时问 4 个 MK 键 | 1 | 4 |
| VT 变量追踪 | `VAR GHTAY = 14673`、`VAR OKOSG = VAR GHTAY` … 5 环链（按文档顺序、相隔很远）+ 4 环干扰链；问哪些变量得到该值，答出干扰链即错 | 1 | 5 |
| 2H 两跳 | "The vault key of the Orrin observatory is held by Kaila Brenn." 与远处的 "The employee badge number of Kaila Brenn is …"，旁有两人的干扰号码；共 2 题 | 2 | 2 |

单答案题必须**恰好**给出正确的码；列表题必须包含全部条目（多出的会记录）。

#### 方法：五处改动，每一处都有一个区分实验

1. **定位打分：取最尖锐的一行，再减去中性提示的。** 原来把所有层、所有头、所有问题 token 的注意力质量求和——
   多数头按位置分配质量（最近处、sink、DCA 的分块模式），淹没了真正盯住关键词的少数头。改为每块取
   (问题 token × 头) 中最大的一行（`reduce="max"`），再减去一句中性提示（"Summarize the text above in one
   sentence."）在同一块上的值（`contrast`，按总量缩放）。相关针的块排进前 32 的比例：

   | 打分 | 256K | 2M |
   |---|---:|---:|
   | 求和（原来） | 16/33 | **1/33** |
   | 最尖锐一行 | 31/33 | 22/33 |
   | 最尖锐一行 − 中性提示 | 31/33 | 29/33 |

   （`complex_256k_diagnose.json`、`complex_2m_v2_diagnose.json`；2M 上原来的求和打分基本失效。）
2. **近端配额。** 2M 第一次完整运行里，VT 第一轮的 32 个块有 25 个落在文档最后约 3 万 token（DCA 的
   同块 / 相邻块区，注意力因位置偏高），5 环只定位到 1 环。改为最后 96K token 按长度占比分配名额
   （至少 1/8），其余名额只在更早的部分里排：同一份诊断里第 1 环在远端排第 26、第 4 环第 0。
3. **行级精读。** 重读的短上下文里有 ~30 块代码、几乎所有相似的针，模型常把问的键配上相邻那行的号码
   （"crimson otter → 7646461"，那是 onyx badger 的）。在短上下文里（注意力回到训练范围内）把问题再
   定位一次、逐 token 打分，只留最好的 12 **行**，按原顺序给模型。256K 单轮：MK 14/16 → 15/16，
   2H 第二题从选错人到选对人。
4. **反馈轮。** 多跳题依赖问题没点名的事实（链上的下一个变量、持钥匙的人）。每轮的回答连同问题一起
   用于下一轮定位与精读（回答取最后 256 token），新增未读过的 8 块；最终答案（`Answer:` 之后的
   数字 / 全大写标识符）连续两轮不变即停，最多 6 轮。256K 上 VT 的 5 环全部定位到（单轮只到 1–3 环）。
5. **作答：先抄、再推、后答；VT 用顺序模拟。** 所有题的指令是"先逐字抄下需要的行，再逐步推理，最后写
   `Answer:`"（预算 1024 token）。VT 另做了探针（9 行干净的 VAR、不经长上下文）：让它"反向找链"的
   8 种问法全错——不是漏掉直接赋值的那个，就是混进干扰链；让它"按顺序执行、记下每个变量的值"，表格
   次次正确，只在最后挑出值为 14673 的那几行时偶尔漏一个（每次漏的不同，从不混进干扰链——干扰链的值
   被算成了另一个数）。所以最后一步用三种说法各问一次、名字取并集（self-consistency）。2M 上草堆是
   大量真实的赋值代码，于是指令还说明"上文是无关代码，只有 VAR 行算数"（RULER 的 VT 模板也这样说）。

#### 坦白的地方

- **VT 的指令是针对任务写的**（按顺序模拟、只看 VAR 行），三种说法取并集也只用在 VT 上。理由见上：
  模型在 9 行干净文本上就做不对反向找链，这不是长上下文的问题；RULER 也为 VT 给了专门的模板。
- **贪心解码不是逐位确定的**（这条 GPU 路径上同一提示两次可能不同），所以每个数字是一次运行；2M 上做了
  四次完整运行和一次只问 VT 的运行，21/21 是第三、第四次。2M 的缓存（34.6 GiB）放不下磁盘（数据盘只剩
  2.9 GB、系统盘 9.1 GB）也放不下 /dev/shm（31 GB），每次都重新 prefill。§4.9 之后（`moe_prefill` 改写）整条流水线是确定的：
  同一份文档从头再跑，每一轮的回答逐字相同。
- **VT 的 5/5 是脆的**（见上）：四次答对里两次是停在轮数上限时恰好对。要让它稳，可以在各轮之间按名字
  投票，或者每轮都问几种说法，再用多次 2M 运行统计成功率；每次 2M 运行都要重新 prefill 20 分钟，还没做。
- **方法是在 256K 上一步步调出来的**（上面五处改动各对应一次失败），再拿到 2M 上验证；改动都是
  通用的（打分、配额、精读、反馈），只有 VT 的指令与取并是针对这一类题的。
- 题型比 RULER 少（没有 CWE/FWE 这类汇总题），针是我们自己写的；草堆是代码，自然语言的针在里面比较显眼。
- 这套机器（容器内存上限 62 GB）上锁页 19 GiB 之前要先让内核丢掉不用的文件页（`posix_fadvise`），
  否则分配会被杀掉。

### 4.8 速度：同一个 2M 任务，问答从 51 分钟到 8.6 分钟

§4.7 第 3 次 2M 运行 prefill 19.9 分钟、21 题 51 分钟（每题 72–803 s）。`scripts/bench_locate.py`
把一轮拆开计时：2M 缓存填随机数（定位的耗时与内容无关，不用 prefill），显存 93 万、主机内存 117 万
token，与真实运行一样。

| 一轮里的环节 | 原来 | 现在 |
|---|---:|---:|
| 定位：问题本身（17 token） | 17.4 s | 2.5–2.8 s |
| 定位：问题 + 上一轮回答（274 token） | 62.8 s | 13.4–13.9 s |
| 精读（7.7K → 162 token） | 4.0–7.0 s | 1.6–2.6 s |
| 作答前 prefill（162 token） | 1.25 s | 0.27–0.44 s |
| 生成 | 55–136 ms/token | 14–20 ms/token |

（`bench_locate_2m_before.json`、`bench_locate_2m_after.json`。这台机器容器只有 16 个 CPU、宿主负载
时高时低，吃 CPU 的环节两次测量能差一倍，表中给的是区间。）

三处改动：

1. **定位：每层只读一遍缓存**（`deepinfer/moe/latent_locate.py`）。原来每层读三遍：问题自己的注意力
   （把 latent 展开成 16 个头再做 flash attention），块质量先算 log-sum-exp、再算质量（各写读一次
   (问题 token × 头) × key 的 fp32 分数矩阵）；2M 时一半以上的缓存在主机内存，每一遍都过 PCIe。现在一个
   Triton kernel 算吸收形式的分数 `q_abs·c + q_pe·k_pe`，每 32 个 key 一步，同一组概率既给出这一块的
   log 质量，也更新 flash 注意力的累加；各行的 log-sum-exp 出来后再把块质量归一化——与原来两遍算的是
   同一个量（`tests/moe/test_latent_locate.py` 对 fp8/fp16、GPU/主机分界、多种 DCA 关系逐项对照）。
   fp8 的缓存段先整体反量化成 fp16 一次（否则每个行块都要再转一遍：274 token 时 590 → 400 ms/层）；
   主机内存的段在另一个 CUDA stream 上提前一段拷进显存。
2. **MoE：专家不再每次从主机内存重传**。`moe_prefill` 用的 `load_experts` 每次都把这一层要用的专家从
   锁页主机内存拷上去（每层 31 ms 的 PCIe），而这些专家早就全部常驻显存。改为直接反量化显存里的打包
   权重：26 层一次从 ~1.2 s 降到 ~0.23 s；不超过 64 个 token 的块走 runtime 自己的融合 kernel。这一处
   同样作用在 prefill 上：2M prefill 19.9 → 16.8 分钟。
3. **生成：一步一个 CUDA graph**（`deepinfer/moe/graph_decode.py`）。原来每个 token 约 3,400 次 kernel
   启动、token 嵌入在 CPU 上查、MoE 在主机上路由（每层两次设备→主机同步），GPU 只忙 ~16 ms。作答的
   上下文很短（几百到两千个位置、fp16、全在显存），一步可以完全不回主机：嵌入表放显存；注意力对整个
   小缓存做，还没写到的位置掩成概率 0；门控的 top-k 直接去索引常驻专家的指针表，交给 runtime 现成的
   指针分组 Q4 kernel；argmax 写回显存喂给下一步。整步录成一个 CUDA graph 重放，每 8 步回主机看一次
   有没有停止符。输出与逐步解码一致——贪心解码在这条路径上本来就不是逐位确定的，两种方式都会在同一个
   接近平局的位置偶尔分叉。

**端到端**（同一份 2M 文档、同样设置，`complex_2m_fast.json`）：

| | §4.7 第 3 次运行 | 加速后（第 4 次） |
|---|---:|---:|
| prefill | 19.9 min | 16.8 min |
| 21 题合计 | 51.2 min | **8.6 min** |
| 每题 | 72–803 s（中位 108 s） | 13–135 s（中位 18 s） |
| 结果 | 21/21、31/31 | **21/21、31/31** |

加速后第 1 轮定位每次 2.5–3.1 s；后续轮（问题 + 回答，长度不等）4.5–15.3 s（中位 7.6 s）；精读 +
作答每轮 2.6–12.7 s（中位 3.7 s；每轮生成 49–782 个 token，中位 119）。VT 各轮名字数 1、5、2、5、5，
第 5 轮与上一轮一致而停，没有混进干扰链。

剩下的时间在哪：prefill 的 16.8 分钟里约 14 分钟是有界编码（每个 token 看前 96K）的 flash attention，
本卡 fp16 算力摆在那；问答里最贵的是带回答的定位（274 个问题 token × 16 个头对 210 万个 key，每层约
20 TFLOP，现在跑到 ~50 TFLOPS）。

**缓存存盘：同一份文档第二次起不用 prefill。** 2M 的 fp8 缓存 34.6 GiB，这台机器哪块盘都放不下
（清掉旧的两份 1M 缓存后，数据盘、系统盘各剩约 20、26 GiB）。`LatentKVCache.save(..., spill=[另一块盘])`
改为每个数组每层一个文件，依次写进第一块放得下的盘，`cache.json` 记下每个文件在哪；每写完一个文件就刷盘
并让内核丢掉它的页缓存（容器的 62 GB 内存上限把页缓存也算进去），加载时主机内存那部分直接读进锁页内存。
`needle_complex.py --save-cache / --save-spill / --load-cache`，加载时核对文档哈希与编码设置。实测：
存盘 98 s（latent 第 0–18 层在数据盘，其余在系统盘）；**从盘加载 51.3 s，原来 prefill 16.8 min**；
加载后的一轮同样 21/21、33 处针全部定位到（`complex_2m_saved.json`、`complex_2m_loaded.json`）。

**流式编码：窗口 96K → 16K。** 有界编码本来就是流式读法——每个 token 只看开头 64 个 sink 加最近一个
窗口——prefill 的大头是窗口里的注意力，和窗口长度成正比。`--encode-window 16384`：prefill
16.8 → 6.8 min（`complex_2m_w16k.json`），33 处针全部定位到，20/21：唯一错的是 VT——5 环都读回来了、
第 2、4 轮也答全了 5 个名字，最后两轮漏了 AVCOU（却写了依赖它的 INRCW）。作答用的是原文 token，编码
窗口只影响定位时读回哪些块，所以这更像 VT 一贯的摇摆，而不是窗口太小。第二次 16K 运行 21/21、31/31（`complex_2m_w16k_2.json`，prefill 同样 6.8 min，VT 第 5 轮与上一轮一致而停）——两次合计 VT 以外 40/40、VT 1/2，与 96K 下 VT 的不稳相当。再往下缩收益有限：
16K 时 6.8 分钟里注意力只剩约 3 分钟，MoE 约 2 分钟，投影、写缓存等约 1.5 分钟。

踩到的两个坑：

- 主机内存段的拷贝放到另一个 stream 后，单测全过，2M 上注意力输出却全是 NaN（块质量正常）：暂存缓冲区
  从计算 stream 的缓存分配器拿，拿到的可能是刚释放、但队列里的 kernel 还在用的显存，拷贝 stream 并不
  知道要等。分配之后先让拷贝 stream 等一次计算 stream。
- 第一次 graph 生成输出一串 "!"：还没写到的位置概率虽然是 0，那片显存却没初始化，0 × inf = NaN。
  生成前把这些位置清零。

### 4.9 3M：同样 39 根针、21 题

| | 2M | 3M |
|---|---|---|
| 序列 | 2,097,152 | 3,145,728 |
| KV（latent fp8） | 34.6 GiB | 51.9 GiB：显存 93 万 token，锁页主机内存 221 万 token |
| 主机内存 | 锁页约 20 GiB | 锁页实占 42 GiB（PyTorch 把锁页分配取整到 2 的幂），容器 62 GiB 上限里用到 58 GB |

| 21 题 | 8–9 min | 14.6 min |
| 结果 | 21/21 | **21/21、31/31，33 处针全部定位到** |

**先照搬 2M 的方法跑了两次 3M**（`complex_3m.json`、`complex_3m_v2.json`）：都是 20/21——MK、MV、MQ、2H
全对，VT 只找到链头。第 1 轮问题本身只定位到 `VAR GHTAY = 14673`；第 2 轮用"问题 + 整段回答"定位，新读
的 8 个块里一条 VAR 行都没有，回答不变，循环就停了。第二次已经加上"问题 + 最终答案"补 4 个块，也没够着。

**诊断**（`scripts/rank_followup.py`，`rank_followup_3m.json`）：3M 上每一跳"下一环"所在块在未读块里的排名——

| 下一环 | 问题 + 整段回答 | 问题 + 最终答案 | 只有最终答案 |
|---|---:|---:|---:|
| OKOSG（第 1 跳） | 154 / 241 | 76 | 14 |
| QHUJP | — | 121 | 22 |
| AVCOU | — | 25 | 5 |
| INRCW | — | 62 | 26 |

2M 上"只有最终答案"把下一环排第 0–1；到 3M（4.9 万个块），注意力定位仍能把下一环排进前 30，但进不了前 8。
只用答案里实体 token 那几行打分（排 17、22、6、25）、去掉中性提示对比（90–180）都不更好。

**改法**：后续每一轮再用 "Answer: <最终答案>"（不带问题）定位一次，补 32 个块——与第 1 轮相同的预算——交给
行级精读去挑行；轮数上限 6 → 8（5 环的链一轮走一环要 6 轮）。3M 上 VT 第 2、3、4 轮依次找到 OKOSG、QHUJP、
其余各环，**21/21、31/31**（`complex_3m_v3.json`，问答 14.6 min）；同一份缓存上再跑一遍，21 题每一轮的回答
逐字相同（`complex_3m_v3b.json`）。从头再 prefill 一次、用命令行默认参数的独立进程（`complex_3m_v4.json`，prefill 25.3 min、问答 14.6 min）同样 21/21，而且 21 题每一轮的回答与上面逐字相同：改写后的 `moe_prefill` 不再让同一个位置在一次 `index_add_` 里收好几份专家输出（fp32 原子加法的次序不定），prefill 也成了确定的。2M 上同样的设置也是 21/21（`complex_2m_follow32.json`）。

VT 第 4 轮的回答已给全 5 个名字，第 5、6 轮又退回 3 个（第 6 轮与第 5 轮一致而停）；最后的 5/5 来自三种
说法取并（两种补充说法各给 4 个名字，合起来正好 5 个）——作答的摇摆仍在，见 §4.7。

**工作台**（`scripts/longctx_workbench.py`）：3M 的缓存 51.9 GiB 放不进这台机器的磁盘，每次实验都重新
prefill 要 25 分钟。工作台读一次，之后把实验脚本丢进一个目录，就在这份活着的缓存上跑：上面的排名实验 2 分钟，
整套 21 题 15 分钟。

**两处显存修复**（VT 多读了块之后才暴露，2M 上一次精读就把显存撑爆了）：`moe_prefill` 不再一次聚出全部路由
副本（16K token 的块从约 2 GB 临时张量降到约 0.45 GB）；精读的逐 token 打分不再分配"行 × 位置"的缓冲。

## 5. 诚实的边界

- **测的是检索，不是推理。** 针是一句话的事实、答案是 7 位数。需要综合多处信息、或依赖远距离
  上下文才能理解的问题，"定位 + 重读"只读回少数几块原文，是否够用没测。有界编码下，相隔超过
  96K 的两段文字在编码时互相看不到——跨段的依赖只能靠提问时的定位把它们一起捞回来。
- **多针会互相混淆**，这是模型能力：128K 九根针同文档只答对 4/9（单独放全对），llama.cpp 同样。
  §4.7 用更好的定位打分、行级精读和先抄后答解决了：2M 上 16 个相似键全对。
- **超出训练长度靠 DCA 外推**，无需训练；256K 内全量注意力仍可用，512K 起明显退化。
- **insert 模式是近似**：针之后的草堆没看到针。128K 上它与真实 prefill（single）结果一致，
  1M/2M 上没有逐深度地用真实 prefill 复核（每次 prefill 要 9–35 分钟）。
- **定位用的是全量注意力质量**：每轮把整个库读一遍（每层，§4.8），2M 上问题本身 ~2.5 s、带 256 个
  回答 token 的 ~5–15 s；更省的做法是用块上界先筛（`latent_retrieval.py` 已有）再精算，未做。
- **块检索的 decode 慢**（0.5–3 s/token）：每层每 token 的选块在 Python 里、还有一次同步，未优化。
- 速度：1M 全量注意力 decode 230–370 ms/token；吸收形式注意力内核 1M fp8 2.61 ms/层
  （264 GB/s，峰值的 36%），整步主要花在流式读专家上。作答用的短上下文 14–20 ms/token（§4.8）。

## 6. 下一步

1. **定位改为两级**：块上界粗筛（6% 的读量）→ 只对候选块精算注意力质量，定位成本降一个量级。
2. **更难的长上下文任务**：多跳与多针已在 §4.7 做了（RULER 式五类）；汇总类（CWE/FWE、LongBench）
   还没做。VT 要做稳：各轮投票、多次 2M 运行的成功率。
3. **检索 decode 去掉 Python 循环与同步**，并把逐层选块合并成一次。
4. 2M 的主机内存部分放**最新**而不是最旧的 token（有界编码只读最近窗口）。
5. 把 V 不补齐的 FlashAttention（或 fp8 注意力）用到 prefill，再省 20–50%。
6. ~~2M 缓存存盘~~：已做（§4.8），分到两块盘，存盘 98 s、加载 51 s。
7. **4M**：KV 69 GiB，主机端要锁约 54 GiB；PyTorch 把锁页分配取整到 2 的幂（latent 一项就成 64 GiB），超出
   容器 62 GiB 上限。要按实际大小锁页（`cudaHostRegister`，或按层分开分配），或让专家改为流式、腾出显存。
