## B. 缺失的主要内容

### B1 · 新增一节：OLMoE 移植（第二个架构）

现有论文只有 OLMoE 的 llama.cpp CPU 对照（51.1 tok/s），**没有本项目自己的实现**。
需要写：MHA + QK-norm（全向量，非逐头）、softmax top-8 不重归一化、无共享专家、
打包专家指针 kernel、融合 gemv、张量核心 prefill。

价值：证明这套栈**不是 DeepSeek 专用**。

### B2 · 同卡 llama.cpp 对照（全项目最强的证据，目前完全缺席）

已有数据（`docs/results/olmoe_sm89_vs_llamacpp.json`、`olmoe_sm89_fused_decoder.json`）：

| 阶段 | llama.cpp b12024 | 我们 | 比值 |
|---|---:|---:|---:|
| decode | 576.7 tok/s | **624.33** | 1.08× |
| prefill | 19,948 tok/s | **23,027** | 1.15× |

方法学部分值得写：**同卡、同模型、同量化、三轮交替、greedy top-5 logits 对齐、CUPTI 逐 kernel 分类**。
这是本文唯一一处「与成熟实现正面对照且不落下风」的结果。

### B3 · 三段 regime 模型（取代 §8.2 的单一带宽模型）

§8.2 现在只有一条「吞吐 ≈ 带宽 ÷ 每 token 字节」。实际测得三个阶段：

| regime | 判据 | 本文位置 |
|---|---|---|
| **主机受限** | 主机 > GPU（4080S 早期：16.4 vs 7.2 ms） | §35 |
| **算力受限** | prefill：512 token 摊薄权重 | §37 |
| **带宽受限** | 两者都消除后：0.741 GB ÷ 481 GB/s | §38 |

**§33「带宽不是约束」和 §38「decode 就是纯带宽问题」并不矛盾——它们描述不同 regime。**
这条必须写清楚，否则论文会被审稿人当成自相矛盾。

### B4 · 158× 优化曲线

| 阶段 | tok/s | 倍数 |
|---|---:|---:|
| 逐专家 Python 循环 | 3.95 | 1× |
| 打包专家 + KV cache | 47.31 | 12× |
| 融合 gemv + CUDA Graph | 247.58 | 63× |
| 稠密也打包 | 624.33 | 158× |

其中收益最大的单个改动是**去掉 fp32 加宽**（1.06× 中的 2.06 倍那一步），
而不是 profile 指出的任何一项——这条方法论值得写进 §7。
