> 形态：技术介绍片（B 站 / YouTube），真人出镜可选，全部用录屏 + 字卡也能成立
> 语言：中文旁白 + 中英双语技术名词

### 镜头 2 ｜ 0:18 – 1:00 ｜ 问题：显存墙

**画面**：简单的示意动画或字卡

**屏幕文字**

```
0.5B → 1GB
3B   → 6GB (FP16)
7B   → 14GB (FP16)
15.7B MoE → 31GB (FP16)
────────────────
你的卡：4GB
```

**旁白**

> 模型的参数量是硬的，显存也是硬的。
> 主流做法要么量化、要么切分、要么换卡。
> 我选择的是第三条最难走的路：**从 kernel 开始，把整个推理栈按 4GB 重新长一遍**。
> 这不是"套一层量化库"，是手写 GEMV、手写 attention kernel、手写 KV 管理。

---

### 镜头 3 ｜ 1:00 – 2:15 ｜ 单卡：量化 + 原生 kernel

**画面**：录屏 —— 打开仓库，`ls deepinfer/moe/`，滚一下 `fused_moe.py` / `paged_mla_kernel.py`

**屏幕文字**

```
W4A16 / W3A16 CUDA GEMV
GQA decode kernel (FP16 / INT8 / FP8)
paged KV + 连续批处理
CUDA Graph（静态路径）
```

**旁白**

> 单卡这条路径做了四件事。
> 第一，权重量化到 4bit 和 3bit，3bit 是把 8 个权重压进 3 个字节。
> 第二，attention 自己写 decode kernel，支持 FP16、INT8、FP8 三种 KV 存储。
> 第三，KV 按 block 分页管理，支持连续批处理。
> 第四，静态路径上把整个 decode 捕获成 CUDA Graph。

**画面**：切到实测数字

**屏幕文字**

| 模型 | 显存 | 速度 |
|---|---|---|
| Qwen2.5-3B W4A16 | 2.49 GiB | **42.7 tok/s** |
| Qwen2.5-7B 混合 4/3bit | 3.20 GiB | **26 tok/s** |
| 7B 整体 Q4 | 3.92 GiB | ~8 tok/s（持续 paging） |

**旁白**

> 结果是：3B 稳态 42.7 token/s，7B 混合精度 26 token/s。
> 注意最后一行的 7B 整体 4bit 只有 8 token/s——**4GB 上"整体 Q4"和"几十 token/s"不能同时满足**，
> 这句话很重要，后面还会回来说。

---

### 镜头 4 ｜ 2:15 – 3:20 ｜ 最难的一块：15.7B MoE 流式

**画面**：录屏 —— 终端里模型文件 `ls -lh` 显示 10GB，然后跑 smoke 脚本

```
-rw-r--r-- 1 umou 197684 10G  DeepSeek-V2-Lite-Chat-Q4_K_M.gguf
```

**屏幕文字**

```
9.65 GiB GGUF —— 从不整体加载
expert 按 chunk 从磁盘流式读入
fused Q4_K/Q5_0/Q8_0 kernel 直吃 packed 权重
峰值显存 2.23 GiB
```

**旁白**

> 这是这个项目最难的一块。
> DeepSeek-V2-Lite 的量化文件有 9.65 GB，而我的卡只有 4GB。
> 解法是：**永远不整体加载**。路由专家按 chunk 从磁盘读进来，用完就丢。
> 权重不做反量化展开，kernel 直接读压缩后的 packed 数据。
> 最终峰值显存 2.23 GiB，decode 2.6 到 3 token每秒。

**画面**：诚实补一刀

**屏幕文字**

```
同一份 Q4_K_M，llama.cpp CPU：9–13 tok/s
→ 这条路径证明的是"能跑通"，不是"更快"
```

**旁白**

> 但我要把话说清楚：同样的模型用 llama.cpp 在 CPU 上跑，有 9 到 13 token/s，比我这快。
> **这条路径证明的是工程可行性，不是性能优势。**
> 我把它写进 README 的第一天就没打算藏。

---

### 镜头 5 ｜ 3:20 – 4:50 ｜ ECS：把专家拆到两张卡上

**画面**：双卡示意（可以用 PPT 画两个 GPU 框 + 箭头）

**屏幕文字**

```
ECS = Expert Coordination System
rank0: attention + shared experts + LM head
rank1: routed experts only（峰值 38 MiB）
NCCL 点对点交换 activation
```

**旁白**

> 第二部分是 ECS，专家协调系统。
> 核心想法很简单：协调卡保留 attention、共享专家和输出层，另一张卡只当"专家执行器"。
> 远端那张卡完全不加载模型，峰值只占 38 MiB。
> 两张卡之间用 NCCL 交换激活值。

**画面**：切到连续批处理数字

**屏幕文字**

```
连续批处理 + paged KV
固定 batch 8 聚合解码：25.90 tok/s（6.17× 单卡）
4 请求 × 44 token：paged 比 dense 快 1.17×
共享 89-token 前缀：wall −26%，单请求 prefill −53%
```

**旁白**

> 在这一层上做了三件事。
> **paged KV**：每个请求自己持有 KV block，按需增长，decode 时整行永远不用搬动。
> 结果是在长上下文下比原来的整块缓存快 1.17 倍，短上下文打平。
> **前缀共享**：prompt 按 block 切块做 hash，命中就复用，只算剩下的后缀。
> 四个请求共享一段 89 token 的前置说明时，总耗时降了 26%，单次 prefill 从 1.17 秒降到 0.55 秒。
> **admission 合并**：空闲期等一下，把一串到达的请求合成一次 prefill，稳定提升 2 到 5 个百分点。

### 镜头 6 ｜ 4:50 – 5:40 ｜ 诚实的限制

**画面**：黑底白字，逐条出现

**屏幕文字**

```
❌ prefill/decode overlap —— 撞上 NCCL 单通信流
❌ worker 池化 —— 只有单测，从未接真流量
❌ collective all-to-all —— 未接入 runtime
❌ 崩溃续跑 —— 整请求重来
```

**旁白**

> 现在说不行的部分。
> **prefill 和 decode 没法真正并行**。我实现了，跑起来直接 SIGABRT。
> 根因不在我的调度器，在 NCCL：一个 process group 的点对点通信跑在同一条内部流上，
> 两个 forward 同时要用就是抢同一条流。
> **worker 池化**写完了分发器，但这台机器只有两张卡，凑不出"一协调 + 两 worker"，所以它从来没跑过真实流量。
> **collective all-to-all** 只有单独的验证，没接进 runtime。
> **崩溃续跑**没有，worker 挂了就是整个请求重来。

**旁白（继续）**

> 所以二卡形态的定位是：**能跑、可复现、token 精确，但不是吞吐机器**。
> 单个远端 worker 串行服务所有专家块，过了饱和点再加请求只换来延迟。

### 镜头 7 ｜ 5:40 – 6:15 ｜ 方法：三次押错

**画面**：三个快切字卡

**屏幕文字**

```
1. 假设"KV 拷贝是瓶颈" → 短上下文根本不成立
2. "先 decode 后 admit"  → 一个 0.5s 阻塞，性能回退 47%
3. 把护栏抛的 ValueError → 当成 NCCL 崩溃写进文档
```

**旁白**

> 这一轮我押错了三次。

> 第一次，我假设 KV 拷贝是瓶颈，做完 paged KV 之后发现短上下文根本没差别，
> 只有长上下文才成立。**如果先花十分钟量一下拷贝占比，能省两天。**

> 第二次，我把调度改成"先 decode 再 admit"，结果其中一个收集函数在没请求时会阻塞，
> 把收益吃成了 47% 的性能回退。

> 第三次最难看。我给一个功能加了护栏，跑测试看到报错，就把"失败"写进了文档还分析了根因。
> 后来发现那次**根本没跑起来**——是护栏自己抛的异常。
> 我把自己写的保护代码的报错，当成了实验结果。

**旁白（收尾）**

> 所以现在我的方法是三条交叉验证：会话日志告诉我意图，git 告诉我代码实际状态，测试告诉我还能不能跑。
> 这一轮开工时 113 个测试通过，收工时 127 个。

## 五、剪辑时容易踩的坑

1. **录屏里的中文可能糊** —— 终端字号调到 18pt 以上，用等宽字体，背景别用纯透明。
2. **`nvidia-smi` 的输出一闪而过** —— 用 `watch -n 1` 或录完再定格。
3. **数字要说全** —— 42.7 t/s 必须带上"静态 Graph 单请求"的限定，否则会被喷口径。
4. **限制段别剪掉** —— 这是这条视频跟"又一个吹牛的 AI 项目"的区别所在，也是评论区会往好方向走的原因。
